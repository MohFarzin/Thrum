

# Build THRUM — full project brief (execute this)

You are building **THRUM** from scratch in this folder. Follow this brief exactly. Do not rename the product. Do not invent alternate product names.

## Identity (locked)

- **Name / spelling:** `THRUM` only (never Thrust, Trump, Thrumm, etc.)
- **What it is:** Open-source self-hosted “tech heartbeat” monitoring platform — web UI + ingest API + alerts.
- **Owner goal:** Freelancer / reusable open-source tool (not a job-placement toy).
- **Related future products (do NOT build now):** `Kastora` (media/voice), `Quicktunnel` (VPS tunnel when no public IP). Design so THRUM can later sit behind Quicktunnel. Mention both only in README roadmap.

**Tagline direction:** If it has a pulse, THRUM hears it.

## Runtime model (locked)

- **Host (server) — preferred:** THRUM runs **entirely in Docker Compose**. Web API, React frontend (served for production), PostgreSQL, Redis, Celery worker, Celery beat, reverse proxy — all containerized as separate Compose services.
- **Pterodactyl panel — all-in-one egg (also locked):** Panel users must get **easy peasy** install: import egg → create server → start. **One container** embeds PostgreSQL + Redis + Gunicorn + Celery + built React (WhiteNoise). **No separate database server, no separate Redis server, no DATABASE_URL / REDIS_URL for the user to fill.** Egg lives in-repo at `pterodactyl/egg-thrum.json`; runtime image `pterodactyl/Dockerfile` (`thrum-pterodactyl:latest`, built once on the Wings node). Document in README.
- **Clients (agents):** Can run **anywhere** (game server, website VPS, home PC, CI). They only need outbound HTTPS to POST heartbeats. No inbound ports required on the client.
- **Also supported without agents:** Server-side **HTTP** and **TCP** polling from the THRUM host containers.

Local / preferred prod: Compose. Panel / quick self-host: all-in-one egg. Same product; two runtimes.

## Stack (locked)

- **Backend:** Python 3.12+, **Django**, **Django REST Framework** (or Django Ninja if you prefer one style — pick DRF unless you have a strong reason)
- **Frontend:** **React** (Vite) + TypeScript
- **DB:** PostgreSQL
- **Jobs:** Celery + Redis (worker + beat)
- **Auth (UI):** session or JWT — prefer simple, secure Django session + DRF for API; or JWT if SPA is fully decoupled. Document the choice.
- **Agent auth:** per-monitor API keys (shown once; **hashed at rest**)
- **Reverse proxy (prod Compose):** Nginx or Caddy in Compose serving the built React app and proxying `/api` (and admin) to Django
- **Package mgmt:** clear `requirements.txt` or `pyproject.toml`; frontend `package.json`
- **Optimize for:** low resource use on old hardware (e.g. home i3), few containers, sensible intervals, DB indexes, retention cleanup, no pointless microservices

## Data model (v1)

**Monitor**

- UUID primary key (public IDs)
- owner (FK User)
- name, type (`http`|`tcp`|`heartbeat`)
- target (nullable for pure heartbeat)
- interval_seconds, timeout_seconds
- expected_status_code (HTTP)
- heartbeat_grace_seconds
- api_key_prefix + api_key_hash (never store raw key)
- status (`up`|`down`|`unknown`)
- last_checked_at, last_heartbeat_at
- consecutive_failures
- is_enabled
- created_at, updated_at
- Indexes on: owner, status, last_checked_at, type

**CheckResult**

- monitor FK, checked_at, success, latency_ms, error_message (short), status_code
- Index on (monitor, checked_at)

**AlertChannel**

- owner FK, type (`email`|`discord`), config JSON, is_enabled

**AlertEvent**

- monitor FK, channel FK, kind (`down`|`up`), sent_at, success, error

## API

### Heartbeat (Simple tier) — clients anywhere

`POST /api/v1/heartbeat/<monitor_uuid>/`  
Auth header: `Authorization: Bearer <api_key>` or `X-Thrum-Key: <api_key>`

Optional JSON body (strict size limit, e.g. 16–64KB):

```json
{
  "status": "ok",
  "message": "optional",
  "metrics": { "players": 3 }
}
```

Responses: `200 {"ok": true}` on success; `401` bad key; `413`/`400` on abuse/invalid.

### Authenticated UI API

REST endpoints for monitors, check results (paginated), alert channels, “check now”, API key rotate — all **object-level owned by current user**.

## Workers / scheduling

1. Enqueue due HTTP/TCP monitors
2. Execute checks with hard timeouts; limited redirects for HTTP
3. Heartbeat watchdog: if `now > last_heartbeat_at + interval + grace` → down
4. Alert only on transitions; optional: require N consecutive failures (default 2) before down
5. Daily retention cleanup for CheckResult

## Security & sanitization (required)

- Hash API keys at rest; show full key **once** on create/rotate
- Rate-limit heartbeat and login
- CSRF strategy correct for SPA+API choice; secure cookies in prod
- `DEBUG=False` in production settings
- `ALLOWED_HOSTS`, `CSRF_TRUSTED_ORIGINS` from env
- Secrets only via env; never commit `.env`
- HTTP monitor URL schemes: only `http`/`https`
- Mitigate SSRF where practical (block link-local/metadata/`169.254.169.254`; document residual risk for self-hosted); prefer optional allowlist mode
- Cap timeouts, body sizes, error message length; do not store raw response bodies
- Escape/safe rendering in React; no `dangerouslySetInnerHTML` for user targets
- Users can only access their own monitors
- Non-root containers where possible
- Do not log API keys, webhook URLs, or SMTP passwords

**Privacy note for README:** future High tier (IPs, player data) is sensitive — not in v1.
